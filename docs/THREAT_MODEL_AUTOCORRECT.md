# Threat model: local autocorrect and the encrypted user dictionary

Scope: the local autocorrect feature described in `docs/AUTOCORRECT.md` and decided in
`docs/ADR_AUTOCORRECT.md` — the tokenizer and checker, the installed Hunspell dictionaries,
the encrypted word list in `autocorrect.sqlite3` behind the `JARVIS/autocorrect/v1` derived
key, the correction and undo path, the explicit AI text improvement through the local
gateway, and the command module that exposes them. Out of scope: the `llama-server` binary
itself, the operating system, the user's own backups, and the correctness of the upstream
word lists.

Assumptions: the master password is chosen by the user; the device may be lost or stolen; any
local process running as the same user can read and write the user's files, including the
dictionary folder and the database; the dictionary files are installed by the user from a
source this project does not control; the executable the user selects as `llama-server` is
not attested; and the interface that drives these commands is not yet part of this
repository, so the guards below are enforced at the command boundary and in the engine rather
than by a UI. Every mechanism quoted below is in the code; the last column says what is left
after it.

# Threats

| # | Threat | Impact | Enforced mechanism | Residual risk |
| --- | --- | --- | --- | --- |
| 1 | Device theft or another local user | A copy of `autocorrect.sqlite3` and its `-wal`/`-shm` siblings exposes the words the user taught the application — names, brands, internal terms — if it can be decrypted | The word list is stored as AEAD ciphertext (`EncryptedRecord`, XChaCha20-Poly1305, entity type and id bound as associated data) under a key derived by HKDF with the label `JARVIS/autocorrect/v1` (`KeyPurpose::Autocorrect`) from the master key, which is wrapped by an Argon2id KEK. `UserDictionaryStore` is built from a `PurposeKeyProvider` that holds only the derived key, and `UserDictionaryPayload`'s `Debug` prints `<redacted>`. A foreign key is not a failure but a report: entries it cannot decrypt are counted in `unreadable`, asserted by `another_purpose_key_cannot_read_a_dictionary_database`. The payload inside the ciphertext is UTF-8 JSON with a `schema_version`, and a payload that fails `validate()` is counted as unreadable rather than used | While the storage is unlocked the words are decrypted into the process, so a local attacker with the same user rights, a memory scraper, or a live forensic capture reads plaintext. Encryption protects the file, not the running process, and the application sets no filesystem ACLs. The **installed dictionaries are public files in a plain folder** by design: they are readable and replaceable by anything running as the user, so a local attacker can change what the checker knows (see threat 4) without touching a key |
| 2 | A process reading the data directory, or a stale copy in memory | Decrypted words, or the text of a document that was corrected, stay reachable after the user locked the storage | `UserDictionaryStore::invalidate()` clears the decrypted entries, the session ignore list, and the unreadable counter; `VaultSession::lock()` sets `self.autocorrect = None` together with the vault store, the memory store, and the master key, whatever the lock path was; `autocorrect_store()` re-checks the unlock state ("Never keep a dictionary key around once the master key is gone") and reports `StorageLocked`; `drop_autocorrect()` drops the key and the words when the user switches checks off while the shared unlock state stays. The undo journal is cleared by `AutocorrectHandle::clear_journals()` on every lock path — an explicit lock (`notes_lock`, `vault_lock`, `memory_lock`), the idle timeout (`VaultHandle` runs an on-lock hook registered in `main.rs`), switching checking off, and application exit before the keys go | Dropping a `Vec<String>` is not zeroization: freed heap pages can survive until reused, and the OS may page plaintext to disk while unlocked; no `zeroize` is applied to the decrypted words or to a `CorrectionBatch`. The idle timeout reaches `clear_journals` through the vault handle's on-lock hook, so no lock path leaves a journal behind; the hook is best-effort by construction (a panic in it is logged and does not undo the lock). The lock is an application correctness rule, not a memory-hygiene guarantee |
| 3 | Text sent to the local model | Document text reaches a native binary the user selected, which could log it, be swapped out, or answer with content designed to mislead | There is no automatic path into the improver: `preview_improvement` runs only from `autocorrect_improve_text`, which first requires `settings.offers_ai_improvement()` (`enabled && ai_improvement`, off by default). The text is passed as delimited data between `===BEGIN TEXT===` and `===END TEXT===` with the rule that everything between the markers is content to rewrite and its intent must be ignored, as a single **user** message, so it cannot become a system prompt. Reasoning is requested off (`ThinkingMode::Disabled`). The secret filter runs on the input before anything is sent (`check_improvement_input`) and on the cleaned answer (`check_improvement_answer`). Results are a preview with `applied: false`, and no improvement record is written to AI memory — the module has no memory store, only three pure helpers (`scan_for_secrets`, `looks_like_instruction`, `clean_model_text`). No token, prompt, or answer is logged: events are counted, and `AutocorrectError` messages carry no content | The endpoint is loopback-only, which protects the text from the network, not from the process listening on the port: a hostile or buggy server reads the whole text it is sent and can answer misleadingly. Labelling the data reduces prompt-injection risk but cannot stop a model from following it. Cancellation sets a flag, so a server that keeps computing after the client stops is not interrupted. The thinking preference is only forwarded when the server's template was seen to mention a thinking switch, so `Disabled` is a request, not a guarantee |
| 4 | A malicious, corrupted, or enormous dictionary file the user installed | A replaced word list makes the checker accept wrong words (masking real mistakes) or report every correct word as a typo; a huge file can exhaust memory or time | A dictionary can only ever be **reported on**, never applied: an issue is a suggestion the user accepts, and the reasons safe auto-correction may apply take their replacement from a mechanical rule or from a rule the user wrote, never from a dictionary. A pair that fails to parse is `DictionaryState::Invalid` with the reason, never `Missing`; an encoding that is not UTF-8 or ISO-8859-1 (read from the affix file's `SET` directive) is refused with "unsupported dictionary encoding: …" instead of being mis-decoded; an affix file that is not valid UTF-8 is refused; a missing pair is `DictionaryMissing` with the exact expected paths. An optional `dictionaries.json` manifest pins the SHA-256 of both files, and a mismatch is reported as `Invalid` ("does not match the manifest checksum") instead of being used silently. A broken manifest is ignored and the pairs still load, so the failure mode is "no verification", never "no checker" | A file larger than `MAX_DICTIONARY_FILE_BYTES` (64 MiB) is refused as `DictionaryInvalid` before it is read into memory, and a directory in place of a file is refused with "is not a file". Nothing verifies a dictionary's provenance unless the user writes a manifest, and the manifest itself is only as trustworthy as the folder it sits in — an attacker who can replace the `.dic` can usually replace the checksum beside it. A hostile list can also shape suggestions: it cannot change text silently, but it can make a plausible wrong suggestion the user then accepts |
| 5 | A stale range, or a document that changed (including because an attacker typed into the editor) | A correction lands on the wrong characters, or an undo throws away the user's own edit | The interface passes the version it checked (`text_version`, the first 8 bytes of SHA-256 as 16 hex characters) and `apply_corrections` refuses the whole request with `StaleText` (`stale_text`) before touching anything. Every `Correction` also carries the `original` text it expects at its range: a correction whose range no longer holds that text is skipped and reported as `Mismatched`, two corrections that touch the same text are `Overlapped`, and a range past the end is skipped rather than clamped. Inside the engine a range that does not fit the text is refused with `RangeMismatch`, and ranges are Unicode scalar offsets converted to UTF-16 in the same pass, so an emoji or a combining mark cannot shift a highlight. An AI preview is pinned twice: `apply_improvement` refuses when `preview.version_before != text_version(current_text)` or when `expected_version` does not match, and a preview that proposes no change or is already applied is refused | The version is a 64-bit prefix of a hash, so a collision is conceivable in principle (it would have to be produced deliberately, and the per-correction text check is the second gate). Omitting `expected_version` — which the signatures allow — drops the whole-text guard and leaves only the per-correction one. An attacker who can type into the editor can already change the text; the guards ensure a correction is never silently applied to characters it was not computed for, but they cannot restore text the attacker deleted |
| 6 | Undo abuse | An undo reverts a change the user did not intend, or the journal becomes a copy of the document on disk | The journal is **in memory only** and holds at most `MAX_JOURNAL_BATCHES` (20) applied batches; it is never serialized. `undo_last` reverts only the newest batch and refuses unless the current text is exactly what that batch produced (`text_version(text) == batch.version_after`), returning `UndoConflict` (`undo_conflict`) otherwise, so a user edit is never overwritten. A batch that changed nothing is not journalled, so undo is never offered for a no-op. The journals are per editor scope and are cleared on lock, on exit, and when checking is switched off; `scope` is validated as non-empty and at most 96 characters | While the storage is unlocked the journal holds **the whole text that preceded each of the last 20 batches** in the process, and it is not zeroized. Every lock path clears it (see threat 2), including the idle timeout, so it does not outlive the key by design. Nothing rate-limits the commands: any caller that can reach the command surface can apply and undo corrections as long as the storage is unlocked |
| 7 | Denial of service through a large text, a large word list, or a large dictionary | The window freezes, memory grows without bound, or the disk fills | Text size, issue count, suggestion count, token length, time, list size, and generation length are all bounded: `MAX_CHECK_CHARS` (200 000) refuses an oversized check with `TextTooLarge` instead of truncating it, `MAX_ISSUES` (500 hard, 200 default) cuts the report and sets `truncated`, `max_suggestions` (8 hard, 5 default) cuts a suggestion list, `MAX_TOKEN_CHARS` (40) drops long tokens, the check stops between words at `timeout_ms` (3 s default, 100 ms…30 s) and sets `timed_out`, `MAX_USER_DICTIONARY_ENTRIES` (20 000) refuses an add with `DictionaryFull` and makes an import stop with `limit_reached`, `MAX_IGNORED_WORDS` (2 000) bounds the session list, `MAX_IMPROVE_CHARS` (20 000) bounds one improvement before anything is sent, `IMPROVEMENT_TIMEOUT` (180 s) cancels a runaway generation, `MAX_IMPROVEMENT_TOKENS` (4 096) bounds the answer, `MAX_CUSTOM_RULES` (200) bounds the rules, and `MAX_DIFF_SEGMENTS` (400) bounds a preview while keeping the word counts exact. The user-dictionary suggestion scan is bounded by a length window of ±2 characters and a Damerau-Levenshtein distance capped at 2 with an early exit, and the parsed dictionaries are cached once instead of re-read per word | The check's deadline is tested **between words**, so one very expensive word can overshoot the budget. A 200 000-character text against a large dictionary is still real work on the async worker, and the only cap on an installed dictionary is the per-file 64 MiB read limit (threat 4). Nothing throttles how often a check is requested, so a caller in a loop is a self-inflicted load. The improvement holds the whole accepted document text in memory, and its request body is bounded only by `MAX_IMPROVE_CHARS` |
| 8 | False positives and false negatives of the secret filter | A credential in the text is sent to the local model, or a harmless text is refused as if it held one | The same `crate::memory::redaction::scan` the memory feature uses runs on the improvement input (before the prompt is built, before the provider is called, and again when the preview is built) and on the cleaned answer; a finding becomes `AutocorrectError::SecretDetected(kinds)` (`secret_detected`), whose `secret_kinds()` returns `SecretKind` values and whose `Display` names them ("a private key", "an API token"). `SecretFinding` carries only kind, span, line, and rule, so the matched text cannot reach a log, an error, a dialog, or the model, and an empty or oversized text is refused before the filter's decision matters | The filter is a **heuristic**: it deliberately reports hex digests and long identifiers (false positives), and it misses a credential written in a shape no rule covers (false negatives) — such a text is sent to the local model. A refusal is also a dead end for the user: there is no override on this path, unlike the memory fact path, so a false positive blocks the improvement with no way forward |
| 9 | A malicious or edited word-list import | An import injects words, removes a word, or leaves entries that cannot be read | The plain-text import path only ever **adds words** through `add_many`, which normalizes and validates each line (non-empty, at most 64 characters, no whitespace, no control character, at least one letter), counts invalid lines instead of storing them, skips duplicates, and stops at the 20 000-word cap. The encrypted import path re-applies `ExportedDictionaryRecord`s (entity id, base revision, tombstone flag, ciphertext) through the conflict-safe engine: an envelope whose `schema_version` is not `1` is refused, a revision collision becomes a retained conflict counted in `conflicts` instead of an overwrite, and a payload that fails AEAD or `validate()` on read is counted in `unreadable` rather than becoming a word. An exported record carries a base revision of `0`, and a local tombstone is respected on the conflict-resolution path, which refuses to overwrite a deleted entry | AEAD proves integrity **under the key**, not authorship: a holder of the master key can craft records that are indistinguishable from legitimate ones, and an import applies each record as written — including its tombstone flag — so a crafted export can remove a word. The import cannot overwrite a newer local revision silently, so the failure mode is extra, removed, or unreadable words rather than a wiped list. The user is the one who picks the file, and the application cannot tell a friend's export from an attacker's |
| 10 | A compromised or swapped model server | A native binary the user selects reads every text sent for improvement and can answer with content designed to be accepted | The improvement path reuses the existing runtime, so it inherits the loopback-only rule (`loopback_address()` refuses any non-loopback host before a socket exists, and `allow_lan: true` is rejected), per-argument process launch with no shell, and the bounded stop of the child this process started. Nothing the model returns is executed: text is rendered as text, there is no tool surface, and no model output reaches the command executor, `SafetyGate`, Lua, or AutoHotkey. Failures are content-free (`AiUnavailable`), a blank or oversized answer is `ModelOutput`, and the result is a preview the user must confirm | The binary is not hashed, signed, or attested, so a hostile server reads the whole text it is sent — which is exactly the text the user asked to rewrite, and may be personal. The loopback rule keeps the text off the network, not away from the process on the port. The user's own confirmation is the last control, and a persuasive rewrite is what the user is least able to check quickly |

# The vault boundary

The password vault is outside this feature, and the boundary is a property of the code rather
than a promise:

* `crates/jarvis-core/src/autocorrect/` names no vault type, no vault method, no vault
  database, and no vault entity type. The only occurrences of "vault" and "password" in the
  module are documentation (explaining that the vault is out of scope and how the key is
  derived) and two test fixtures that use the literal string `password: FICTIONAL_SECRET_VALUE`
  to prove the secret gate fires. There is no `VaultStore`, no `EncryptedVaultStore`, no
  `VaultSession`, no `reveal_secret`, and no `VaultItemPayload` anywhere in it.
* The store the checker uses is handed to it: `LocalSpellChecker::check` borrows the
  `UserDictionaryStore` of the unlocked session, and that store reads and writes exactly one
  entity type, `SyncEntityType::AutocorrectDictionary`. A record of another type is ignored
  when the record list is built, so a password record inside the same repository is invisible
  here.
* Nothing scans vault content for secrets, because nothing here can reach it. The secret
  filter is applied to the text the user asks to improve and to the answer — not to a vault
  record, and not to the word list.
* `crates/jarvis-gui/src/tauri_commands/autocorrect.rs` reaches the shared session only
  through `storage_status()` and `with_autocorrect(...)`; it uses `VaultPaths::production()`
  to locate the data directory, which is a path helper, not secret material. It never opens
  the vault store, and no command in it accepts a vault item id.

**The boundary is enforced by a structural test.**
`crates/jarvis-core/tests/autocorrect_isolation.rs` scans every module of the feature and the
autocorrect command module for vault identifiers (`VaultStore`, `EncryptedVaultStore`,
`VaultSession`, `reveal_secret`, `vault.sqlite3`, `JARVIS/vault`, `KeyPurpose::Vault`,
`vault_record`) and for `state.vault`, and it also fails if a command is named after the
vault. It scans the *dependency*, not the wording, so the legitimate use of `VaultPaths` (a
path helper) and `StorageStatus` (the unlock gate) is allowed while a real vault handle is
not. The behavioural half is covered as well:
`another_purpose_key_cannot_read_the_word_list` (in `crates/jarvis-core/tests/autocorrect_storage.rs`)
proves a dictionary database cannot be read with a foreign purpose key, and the memory tests
prove the memory store cannot read a password record.

# Cross-cutting residual risks

* **A word list is not anonymous.** The words a person teaches a checker can name their
  employer, their projects, their medication, or the people they write to. It is encrypted,
  but it is a small file and its meaning survives decryption.
* **One master key protects notes, passwords, memory, and the word list.** Purpose-derived
  keys and separate databases separate the files and the ciphertexts, not the human secret.
* **The undo journal is the least protected copy of the document.** It lives in memory, holds
  up to 20 whole versions of the text, and is not zeroized. Every lock path clears it — an
  explicit lock, the idle timeout (through the vault handle's on-lock hook), switching checks
  off, and application exit — but a freed page can survive until the allocator reuses it.
* **The interface enforces the flow; the commands enforce the rules.** The panels send the
  version they checked, show the whole difference before an AI change, refuse to apply a
  preview that changed nothing, and require an explicit confirmation for a plaintext export.
  A caller that talked to the commands directly would still be refused by the version guard,
  `is_applicable`, `MAX_IMPROVE_CHARS`, and the `confirmed: true` requirement, but a future
  view could bypass the intended user experience. `AutocorrectError` messages are English
  only, like the other features' errors.
* **The AI improvement is the only path that can silently change meaning, not text.** The
  preview makes the change visible and reversible, but a user who confirms a rewrite without
  reading it has accepted whatever the model produced.
